## Context and scope

The multi-check proposal was accepted and implemented today: `main` now runs
every check through `git-hygiene run <hook>`, backed by a check registry,
declaration files, layered settings and a five-code exit contract. It
rejected the `pre-commit` framework on two grounds. The framework's current
release needs Python 3.10, and it has no way to tell a required check from an
optional one.

Neither ground held once it was measured. `pre-commit` 2.17.0, the newest
release that installs on Python 3.6, installs and runs these hooks on the
RHEL 8.10 replica, provided the package builds at the floor and the manifest
admits that version (`spike/build-at-floor`, `spike/pre-commit-at-floor`, and
decisions 0013 to 0015). Whether a check is required can be carried by the
check's own arguments. The dispatcher is therefore a second framework that
this project would maintain alone, and it has not yet been published: `main`
is three commits ahead of `origin`.

This proposal covers the front end only. Filename-authoritative term classes,
which landed in the same series, are unaffected.

## Goals

`pre-commit` is the single way checks are composed, ordered and run, on
modern hosts and at the floor alike. The floor version is 2.17.0, pinned; a
modern host may run any later release.

Every check this package ships keeps its behavior under the framework. That
includes refusing when a repository requires a private term list and none
resolves, and correcting file modes on the first commit.

The published interface keeps working. The hook ids `deny-terms`,
`deny-terms-msg` and `audit-tree`, and the console scripts `check-identifiers`,
`audit-tree` and `install-hooks` from `v0.1.0`, behave as they did at that tag
unless this proposal names a change.

The package carries less code than it does at `3506c93`.

## Non-goals

**Converting the sibling tools.** Their checks become entries in a
repository's `.pre-commit-config.yaml`, but writing those entries, or
manifests for those tools, belongs to their own repositories.

**Backporting framework fixes to 2.17.0.** The pin is accepted as frozen. A
defect that matters gets a workaround in the check or a targeted backport,
decided when it appears.

**Keeping the id-only configuration rule.** See "Security surface" below.

## The design

A check is a console script with a hook entry in `.pre-commit-hooks.yaml`.
Composition, ordering, file selection, skipping (`SKIP=<id>`) and stashing of
unstaged changes are the framework's. The package keeps four scripts and
retires the rest.

| Unit at `3506c93` | Fate |
|---|---|
| `dispatch.py`, `checks.py`, `settings.py`, `gitconfig.py`; the `git-hygiene` script; declaration files; `.git-hygiene` and `.git/info/git-hygiene` | removed |
| `check-identifiers --exit-contract 2` and `GIT_HYGIENE_EXIT_CONTRACT` | removed; they have no caller once the dispatcher is gone and were never published |
| `normalize-file-modes` (`filemode.py`) | kept, gains a hook id, and sets the working file's mode as well as the index's |
| `install-hooks` | kept, restored to the direct shims of `v0.1.0` |

### Required checks

`check-identifiers` gains `--require-private`, with the environment variable
`GIT_HYGIENE_REQUIRE_PRIVATE` and the negation `--no-require-private` beside
it, as decision 0010 requires. With it, failing to resolve any private term
source is a refusal (exit 1), and the message names every location probed and
no term. Without it, absence passes silently, as it does today. A repository
requires the list by adding the flag to the hook's `args:` in its tracked
config. One machine can require it for every repository by setting the
variable. The case the multi-check proposal built a layer for (a moved or
freshly cloned working copy that lost its list) is covered by the tracked
form.

"Not applicable" needs no code. A text check given only binary files already
exits 0 under contract 1, and a manifest entry may narrow itself with
`types: [text]`, which the framework reports as skipped.

### File modes

The framework runs `git diff` before and after each hook and fails a hook
whose run changed it. Changing only the index mode does change it when
`core.fileMode` is true, so the commit is refused once and lands on the
second attempt (`spike/pre-commit-at-floor`, cases `filemode_true_*`).
Setting the working file's mode to match the index leaves `git diff`
unchanged. A probe on the replica with 2.17.0 landed such a commit on the
first attempt, including a partly staged file, whose unstaged half the
framework had set aside and put back with the new mode. `filemode.py` keeps
`--cacheinfo` for the index and adds the matching `chmod` on the working
file. The probe is folded into the spike as part of the change.

### Floor hosts

A RHEL 8.10 host needs `pre-commit` 2.17.0 and its dependency closure, which
`spike/pre-commit-at-floor/packages.tsv` already pins by hash. The manifest's
hooks use `language: python`, so on first use per revision the framework
clones this repository and builds the package into a virtual environment. That
needs network access, or `PIP_FIND_LINKS` pointing at a local copy of the
pinned wheels. A host that cannot provide either uses a `repo: local` entry
with `language: system` and the package installed once; the README shows both.

`install-hooks` stays as the path for a host with no framework at all. None
is known today; keeping the script costs a revert, while removing it would
break `v0.1.0` users and take a major version.

## Alternatives considered

**Keep the dispatcher as built.** It works and is tested, and it keeps the
id-only rule and settings layers. It also makes this project the sole
maintainer of a hook framework, which is the cost the ladder's battle-tested
tier weighs against, and the two facts that justified it did not survive
measurement.

**Run the dispatcher as one `pre-commit` hook.** Framework users would keep
the layering and the exit contract. Every line of the dispatcher would stay,
and a repository would configure checks in two places.

**Require a current `pre-commit` and drop the floor from the framework path.**
This fails on correctness: RHEL 8.10 hosts are the ones these hooks protect.

**Maintain a fork of a current `pre-commit` backported to 3.6.** Decision
0008 declined patching the framework on maintenance grounds, and a fork is
the larger version of that patch. A frozen release plus targeted fixes buys
the same floor for less.

**Native shims only (`install-hooks`, as at `v0.1.0`).** Nothing composes
checks from different tools, which is the problem that started the
multi-check work.

## Cross-cutting concerns

**Security surface.** The dispatcher's rule was that tracked configuration
could name only checks the person had already installed, so that cloning a
repository could never be enough to run code from it. That rule was the
multi-check proposal's own reasoning, not a recorded instruction. Under
`pre-commit`, a tracked `.pre-commit-config.yaml` can name any command
through a `repo: local` entry, and once hooks are installed in a clone, a
pull that changes the file changes what the next commit runs. Nothing runs
before the person runs `pre-commit install` in that clone, and a repository's
tests and build scripts already run its code whenever they are used. This
proposal accepts that risk, which is the framework's standing model. Pinning
`rev:` to tags and reviewing changes to the config file are the mitigations.

**Compatibility.** Hook ids are unchanged; `normalize-file-modes` is an added
id, a minor change. The console scripts from `v0.1.0` remain.
`git-hygiene`, `--exit-contract` and the declaration format were never
released, so removing them breaks no published interface.

**Migration.** This repository's own `.git/hooks/pre-commit` still belongs to
the removed tool; it becomes `pre-commit install` with a
`.pre-commit-config.yaml` naming this repository's hooks. Any clone on this
workstation holding a shim that calls `git-hygiene run` is found by its
marker and reinstalled.

**Idempotency.** `install-hooks` keeps its reseed-from-template behavior and
its marker rule. It also removes the dispatcher-era shims it wrote, which
carry the same marker, for hooks the restored version no longer installs.

**Failure and rollback.** Rolling back is reverting this change's commits;
the dispatcher returns intact, since nothing is migrated on disk beyond hook
files that `install-hooks` rewrites.

**Order of landing.** Branch `floor-build-tools` lands first, renumbered after
decision 0012 (as 0013 to 0015), since this change depends on its build pins
and manifest minimum. This change then lands as new commits on `main`, and
decision 0016 supersedes 0012.

## Verification criteria

Every criterion is an automated test, or a spike registered in
`test/spike-regen.tsv`, and passes on the replica (Python 3.6.9, git 2.43.7,
`pre-commit` 2.17.0 on `PATH`).

1. `pytest` passes with no skips caused by a missing `pre-commit`.
2. `test/spike-regen.sh` reports every spike regenerated, including a new
   case in `spike/pre-commit-at-floor` where a mode fix setting both modes
   lands on the first commit with `core.fileMode` true, and a partly staged
   file keeps its unstaged half.
3. Through `pre-commit try-repo`: `deny-terms` passes clean content, blocks a
   planted term without printing a private one, and, with `--require-private`
   in `args:`, refuses when no private source resolves and names the probed
   locations.
4. The same refusal happens with `GIT_HYGIENE_REQUIRE_PRIVATE=1` and no
   argument, and does not happen without either.
5. A commit whose staged set is a single binary file passes `deny-terms`.
6. `normalize-file-modes` through the framework: a staged 0644 file starting
   with `#!` lands as 100755 on the first commit, and a path listed in
   `.gitmodes-exceptions` keeps its staged mode.
7. `pre-commit-validate-manifest .pre-commit-hooks.yaml` exits 0.
8. `git-hygiene`, `dispatch.py`, `checks.py`, `settings.py` and `gitconfig.py`
   no longer exist, and `check-identifiers --help` does not mention
   `--exit-contract`.
9. `install-hooks` twice produces byte-identical shims that call
   `check-identifiers` directly, and removes a marked dispatcher-era shim for
   a hook it no longer installs.
10. `Architecture.md` and the README describe the framework as the front end
    and mention neither the dispatcher nor its settings files.

## Open questions

1. **The security surface.** Accepting the framework's model means giving up
   the id-only rule described above. This is a policy choice.
2. **History on `main`.** The dispatcher commit has not been pushed. It can
   be removed by new commits on top, as this proposal assumes, or by
   rewriting the three unpushed commits so that it never appears. The rewrite
   needs your instruction.

## Implementation decision log, 2026-09-16

Accepted by the operator under make-it-so. Each entry names the ladder tier
that settled it.

**Both open questions** (operator). Accepting the proposal accepted its
security stance. No instruction named a history rewrite, so the dispatcher
leaves `main` through new commits, as the proposal assumed.

**How `floor-build-tools` landed** (default). A rebase would have renumbered
three decisions across six commits and conflicted in most of them. The branch's
net change was applied to `main` as one commit, `66b1656`, with its decisions
renumbered 0013 to 0015 and the dispatcher's console scripts carried into
`setup.cfg` so that the commit stays green on its own.

**The environment requirement covers the message check too** (default). One
variable names one list; a machine that requires it requires it for every
check that reads it. A separate variable for messages would add flexibility
nobody has asked for.

**What passes under a requirement** (correctness). A staged set with nothing
readable as text passes, because nothing could have been checked; this keeps
the behavior contract 2 gave a binary-only merge. A missing message file
passes as it always did under contract 1, since git always supplies one and
its absence means the hook was invoked by hand.

**How the working file gets its mode** (correctness). A native Windows
`os.chmod` cannot set the executable bit that Cygwin git reads, so where the
working file holds the staged blob, git rewrites it with
`checkout-index -f`. Only a file whose content differs, which cannot happen
under the framework, falls back to `chmod`. Measured on the replica through
the framework and directly; the Windows-interpreter cell is unmeasured, as
Windows Python is not available to this run.

**`normalize-file-modes` exits** (correctness). Under the framework any
non-zero code fails the hook, so "no regular file staged" is 0 and "outside a
work tree" or a refused index update is 1. An unusable exceptions file stays
2.

**The sdist test's skip condition** (correctness). It required
setuptools 61, which the floor pins contradict; any setuptools reads
`setup.cfg`, so presence of setuptools and setuptools_scm is the condition.

**The earlier spike joins the rerun register** (diagnosability).
`spike/pre-commit-python-floor` is registered in `test/spike-regen.tsv`, so
every spike a decision cites is certified by one command.

**Manifest descriptions** (default). The `deny-terms` description still
described the single-file behavior of `v0.1.0`; with the file open for the new
hook id it now names the layered lists and `--require-private`.
