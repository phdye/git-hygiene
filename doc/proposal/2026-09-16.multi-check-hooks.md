## Context and scope

Three separate tools install git hooks on this workstation, and each one
believes it owns the file it writes.

This project owns `deny-terms` and `deny-terms-msg`, and ships `install-hooks`
to place them without the `pre-commit` framework. A second tool owns
`commit-msg` and `pre-push`, refusing forbidden attribution and the wrong
committer identity for a destination. A third owned `pre-commit` in several
repositories, refusing credential-shaped strings and normalizing file modes on
the way into a commit; it was removed from one repository on 2026-09-16 at the
operator's instruction.

Because each tool writes its own hook file, a repository gets the checks of
whichever tool installed last. Only the third offered a way out, through a
drop-in directory its hook ran before its own gate. That directory was the
recommended home for a fourth check under discussion at the time, and it went
away with the tool that provided it. A repository can now have one tool's
checks or another's, and nothing composes them.

The scope here is the front end: how checks are declared, selected, ordered and
run, and what happens when one cannot run. The checks themselves keep their
present behavior.

## Goals

One installer places one hook file per git hook, and that file dispatches to
every check the repository has selected.

A check that cannot run says so rather than passing. The distinction that
matters is between a check that looked and found nothing, a check that had
nothing of its kind to look at, and a check that could not look at all. Today
the last two are indistinguishable in at least one implementation, and the
consequence is either a false refusal or a false pass depending on which way
the author guessed.

The deliberate silent pass when a private term list is absent survives as the
default. It is recorded as intentional in this project's own instructions, for
a stated reason: a contributor cloning a public repository will not have one,
and a check they cannot see must never block their work. A repository that
needs the opposite says so explicitly (see "What a repository may say").

The two sibling tools' checks can be adopted without altering what they
enforce.

Existing hook ids and console-script names keep working. They are a public
interface: a consumer pins a revision and names an id.

The whole arrangement continues to work without the `pre-commit` framework,
on hosts where the framework is not installed (decision 0008). The git floor
is 2.43.7, the version RHEL 8.10 ships, so git's version no longer rules the
framework out on any supported host.

## Non-goals

**A general task runner.** Formatters, linters and builds have a framework
already and this is not a second one. The checks here share a single property:
each can refuse a commit, and refusing is all any of them does.

**Replacing `pre-commit` for consumers who can use it.** Where git is modern
and a project already runs the framework, that path stays first-class and the
manifest keeps describing it.

**Bundled rule content of any kind.** No term list, no pattern file, no
example. The rule that content lives outside every repository is what makes
this project safe to publish, and a framework that ships a sample denylist has
broken it whatever the sample contains.

**Rewriting content.** A check never changes what a staged file contains.
There is one narrow exception to reporting only: a check may declare that it
changes index metadata, meaning the mode recorded for a staged path. File-mode
normalization is that check. It runs by default, and a repository may disable
it (see "Checks that change the index" below).

## The design

A check is a console script plus a declaration. The declaration is what the
dispatcher reads, and it carries seven things: the id, which git hooks the
check runs on, which paths it cares about, whether the repository requires it,
where it sits in the order, whether it changes index metadata, and which exit
contract it speaks.

The dispatcher is a single console script, invoked by a shim as
`git-hygiene run <hook-name>`. One shim per git hook, and the shim stays as dumb
as it is today: find the dispatcher on PATH, fail loudly if it is absent, hand
over. Logic never goes in the shim, because the shim is the one file that a
package upgrade cannot replace.

### The exit contract

The whole design rests on five exit codes rather than three, generalizing the
status vocabulary `resolution.py` already uses for term sources.

```
0  ran, nothing to report
1  ran, found something; refuse the commit
2  usage error
3  not applicable: nothing of this check's kind was staged
4  could not run: a required input was absent or unreadable
```

Three and four are the new ones and they carry the weight. A text scanner
faced with a commit of one generated binary returns 3, and 3 is never a
refusal. That case is not hypothetical: a merge resolving a single binary
file was refused on 2026-09-16 by a gate that could only say "nothing was
scanned; refusing to pass", and the only way past it was to disable hook
verification entirely, which turned off every other check at the same time.

Four is a refusal if and only if the repository declared the check required.
This is the same rule `resolution.py` applies to term sources today, where a
source named explicitly is loud when absent and one found by probing is
silently skipped, and it generalizes without modification: a check the
repository asked for by name must announce that it could not run; a check
enabled by default may stand down quietly.

### Contract versions

The dispatcher cannot tell from an exit code alone which vocabulary produced
it. An older check might exit 3 or 4 for reasons of its own, and read under
the table above, either code would turn a failure into a pass. So the
declaration states the contract, and the dispatcher reads codes only through
the one declared.

```
contract 1  0 pass, 1 refuse, 2 usage error
contract 2  the five codes above
```

A declaration that names no contract is contract 1, so an unconverted check
needs no edit to keep its old meaning. A code outside the declared set is
never read as a pass or as not applicable. It refuses the commit, whether or
not the check is required, and the message names the check, the code, and the
contract it was read under. A declaration naming a contract the dispatcher
does not know is a usage error, reported before any check runs.

### Selection and ordering

Check selection is a fact about a project rather than about a person, so it
belongs in the repository, unlike the term lists. The layered resolution model
already built for terms applies unchanged: system, user, repository, per-clone
under `.git/info/`, environment, and an explicit flag, lowest precedence first.

Order is explicit in the declaration, with a stable sort by id to break ties, so
that adding a check never silently reorders the others. Checks that change
index metadata run before checks that read the staged set. The removed tool had
this right and stated why: a step that re-stages a file must finish before a
gate reads the staged set.

### Checks that change the index

File-mode normalization has to happen without anyone asking for it, so the
front end admits a check that changes the index. The class is limited to
metadata. `git update-index --chmod` rewrites the mode recorded for a path and
leaves both the staged blob and the working tree alone; a partly staged file
therefore comes through intact, and the dispatcher needs no stash-and-restore
step (the machinery `pre-commit` carries for exactly this case). A check that
rewrote content would need that step, so no such class exists.

A metadata check prints one line for every path it changed, on every run,
whether or not `--verbose` was given. Where `core.fileMode` is true, `git
status` will afterward show the working file's mode differing from the index.
The message says so, because otherwise the difference looks like a fault. The
normalization rule itself is the removed tool's, carried over unchanged. This
proposal does not restate it; the implementation takes it from that tool's
source.

### What a repository may say

A repository's configuration may enable a registered check, disable one, set
required or optional, and nothing else. It may not name an executable.

That restriction is the security boundary. A configuration file that could
name an arbitrary command would make cloning a repository sufficient to run
code from it, which is a considerably worse failure than any this project
prevents. Resolution is from id to a console script already installed on PATH,
so a repository can choose among checks the person has installed and cannot
introduce a new one.

A repository may mark a check required even when the check's input lives
outside the repository, as the private term list does. The case this serves is
a repository moved or cloned onto a machine its private list did not reach:
commits there must fail rather than pass with nothing enforced. A per-clone
setting cannot cover that case, since a fresh clone does not carry
`.git/info/`, so the tracked layer has to be able to say it. The cost falls on
anyone who clones such a repository without the list. That is why the silent
pass stays the default, and a repository leaves it only by declaring the check
required in its tracked configuration.

For `deny-terms`, required means at least one private-class term source must
resolve. When none does, the refusal names the check and every location it
probed, and prints no term.

## Alternatives considered

**Keep three tools and give each an extension point.** The arrangement that
existed until this week. Ordering across tools is undefined because no tool
knows about the others, each installer competes for the same hook file, and an
extension point vanishes when its host is uninstalled. That last one is not a
prediction; it is what happened on 2026-09-16, and it is why this proposal
exists.

**Adopt `pre-commit` as the single framework and publish each check as a hook
repository.** The most conventional answer, and it fails on a constraint this
project has already recorded: some hosts have no framework installed, and
decision 0008 keeps the native path for them. On the 3.6.8 floor it cannot be
installed at all, since `pre-commit` 4.6.2 declares `Requires-Python: >=3.10`
in its wheel metadata. That reading was taken by hand on September 16, 2026;
the implementation turns it into `spike/pre-commit-python-floor/` (see
"Verification criteria") so the claim can be rerun. More decisively, the framework
has no way to express the difference between a check that is optional and one
the repository requires, which is the distinction the exit contract exists to
carry. (An earlier draft also cited git 2.21 here. That version came from a
stale test environment; the floor is 2.43.7, which the framework accepts.)

**Rebuild the drop-in directory: a shell dispatcher running every executable in
`pre-commit.d` in name order.** Cheap, and it was working until this week. It
has no declaration, so there is no applicability, no required-versus-optional,
and no way to tell a missing drop-in from one that passed. Ordering by filename
prefix is the convention it forces, which is how every such directory ends up
with `10-`, `15-`, `17-` and an argument about renumbering.

**One console script with subcommands for every check.** Simplest to write and
wrong on dependencies: the checks do not share them, they will not share a
release cadence, and at least one has to remain installable on its own on a
machine where the others are not wanted.

## Cross-cutting concerns

**Compatibility.** Hook ids are an API and this proposal adds none and renames
none. Exit semantics do change, though: a check that begins returning 3 or 4
where it previously returned 0 or 1 is a breaking change for anyone invoking it
directly, and it takes a major version. Under the dispatcher, the declared
contract carries the change: a check moves to contract 2 in the same release
that starts returning 3 or 4, and until then it is read as contract 1.

**Migration.** Installed hooks carry a marker comment and the installer leaves
unmarked files alone without `--force`, so a repository holding a sibling
tool's hook is not trampled. Moving such a repository across is a deliberate
one-time step: uninstall the old tool's hook, install this one, name the checks.

**Idempotency.** Reseeding from a fixed template on every run, which is what
`install-hooks` already does, so an upgrade cannot leave a stale line behind.

**Failure and rollback.** Uninstalling removes only marked files. A repository
with no configuration runs the default set, and a repository whose
configuration names an unknown id is a usage error at commit time rather than a
silent skip, because an id that resolves to nothing is indistinguishable from a
check that passed.

## Verification criteria

Acceptance requires every criterion below to exist as an automated test in
this repository's `tests/`, driving real git repositories through the
installed shims rather than calling functions directly. A test asserts on the
message as well as the exit code, because a crashed run and a refusing run can
share a code. Where a criterion says a term is never printed, the test plants
a known term and asserts it is absent from both output streams.

The suite must pass on the designated host: the pinned 3.6.9 interpreter with
its pinned pytest, against git 2.43.7, the floor. CI is set aside until a
RHEL 8.10 runner exists (decision 0014), so no CI result stands in for that
run. `pre-commit validate-manifest` passes as well.

### Evidence and packaging

`spike/pre-commit-python-floor/` holds a script and a dated transcript that
fetch the pinned `pre-commit` wheel, verify its sha256, and state as a verdict
whether its `Requires-Python` admits 3.6.8. Only the verdict is compared on a
rerun; the version strings ride along in the transcript's header. The script
reads package metadata only, so running it off the designated host is valid
for this one fact.

`spike/` never ships. The source distribution built from a tagged commit
contains no path under `spike/`, and a test asserts it (setuptools_scm
otherwise includes every tracked file; `prune spike` in `MANIFEST.in` is the
expected remedy).

### Installation

Running `install-hooks` twice produces byte-identical hook files.

An unmarked `.git/hooks/pre-commit` is left untouched without `--force`, and
replaced with it. Uninstalling removes only marked files and leaves a foreign
hook in place.

Each installed shim invokes `git-hygiene run <hook-name>`. With `git-hygiene`
absent from PATH, the shim refuses and says what is missing. `git hygiene run
pre-commit` reaches the same dispatcher.

The existing hook ids, `deny-terms`, `deny-terms-msg` and `audit-tree`, and the
existing console scripts keep working unchanged.

### The exit contract

A commit whose staged set is a single binary, in a repository whose only check
is a text scanner, succeeds. This includes a merge commit resolving only that
file. The dispatcher reports the check as not applicable under `--verbose` and
says nothing otherwise.

A required check whose input is absent refuses the commit, and the message
names both the check and the input it wanted. An optional check whose input is
absent passes, and is reported only under `--verbose`.

A declaration naming no contract is read as contract 1: 0 passes, 1 refuses,
2 is a usage error.

A contract 1 check that exits 3, and another that exits 4, each refuse the
commit, even when the check is optional. The message names the check, the
code, and contract 1.

A contract 2 check that exits a code above 4 refuses the commit, whether or
not it is required, and the message names the code.

A declaration naming an unknown contract fails with exit 2 before any check
runs, and the test asserts that no check was executed.

### Configuration

A repository configuration naming an unregistered id fails with exit 2 at
commit time and names the id.

A repository configuration naming a path rather than an id is rejected, and
the test asserts that the rejection happens before anything is executed.

A tracked `.git-hygiene` containing `include.path` does not pull in the
included file; a setting placed only in that file has no effect.

Each layer overrides the one below it: a per-clone `.git/info/git-hygiene`
overrides the tracked file, the environment overrides both, and an explicit
flag overrides everything. `--explain` names the layer each effective setting
came from.

A repository may enable a registered check that the default set leaves off,
and that check then runs.

### Registration and ordering

A check registered through a declaration file is found and run. The suite
covers a check that is not a Python program, and one installed under a
different interpreter from the dispatcher's.

Adding a check with a new id leaves the relative order of the existing checks
unchanged, and checks declaring the same position run in id order.

### File-mode normalization

A commit staging a file whose mode the normalization rule rejects lands with
the corrected mode, with no option given.

The staged content and the working tree are byte-identical before and after,
including when the file is only partly staged.

The output names every path whose mode changed, with and without `--verbose`.
With `core.fileMode` true, the message also says that `git status` will show
the working file's mode differing from the index.

A check that reads the staged set, run in the same commit, sees the corrected
mode, which proves the ordering rule.

A repository that disables normalization in its tracked configuration keeps
the mode as staged. So does a clone that disables it in
`.git/info/git-hygiene`.

### A required private term list

A repository whose tracked configuration requires `deny-terms` refuses a
commit on a fresh clone where no private term source resolves. The message
names the check and every probed location, and prints no term.

The same refusal happens after the working copy is moved to a directory whose
ancestors hold no `.deny-terms.private`, when the list it had relied on lived
in its former ancestor directory.

The commit succeeds once a private list is placed in any one probed location;
one resolving source is enough. A public `.deny-terms` alone does not satisfy
the requirement.

A clone that requires `deny-terms` only in `.git/info/git-hygiene` behaves the
same way, and a repository that does not require the check still passes
silently when no private list exists.

## Resolved questions

Each was settled on September 16, 2026. The tier named in parentheses is the
one that decided it.

**Configuration format** (battle-tested). git-config syntax, read with
`git config --file <path> --no-includes`. TOML and YAML fail on correctness
first: the package has no runtime dependencies and supports Python 3.6.8,
while the standard library's TOML reader arrived in 3.11. Of what remains,
git's own parser is the one this package already relies on, and
`--show-origin` tells `--explain` which layer a setting came from.
`--no-includes` stops a tracked file from pulling in others.

**Configuration file name** (default). `.git-hygiene` at the repository root,
tracked, and `.git/info/git-hygiene` for the per-clone layer, read the same
way. The names follow `.deny-terms` and `info/deny-terms`.

**Whether a repository may enable a check** (flexibility). It may. Because of
the id restriction, a hostile repository can only switch on checks the person
already installed, and the worst it achieves is refusing its own commits. It
may also mark a check required, including one whose input is a private list.

**Index-mutating checks** (correctness). File-mode normalization is a
requirement and must run without being asked, which rules out turning it into
a refusal or leaving it out. A general mutating class fails on the same tier,
since it is not correct for partly staged files without a stash step. What is
admitted is metadata only, enabled by default, and a repository may disable it.

**Absorbed or separate packages** (correctness). Separate packages, each
registering through a declaration file in a system or user data directory.
Absorbing is out because at least one check must stay installable alone.
Python entry points are out as well: they are visible only inside the
environment that installed them, and this workstation runs checks under more
than one interpreter. A declaration names a console script on PATH, which
works whatever language the check is written in.

**Dispatcher name** (default, accepted by the operator). `git-hygiene`,
invoked as `git-hygiene run <hook-name>`. It matches the package, git finds it
as `git hygiene`, and a `run` subcommand leaves room for `list` or `explain`
later without reading a hook name as a command.

## Implementation decision log, 2026-09-16

Each entry names the ladder tier that settled it.

**`deny-terms` speaks contract 2 only when asked** (correctness). A direct
caller, the `pre-commit` framework among them, reads any non-zero code as a
failure, so `check-identifiers` gained `--exit-contract 2` (and
`GIT_HYGIENE_EXIT_CONTRACT`) and the built-in declarations pass it. Direct
callers see no change and no major version is needed.

**What `deny-terms` returns under contract 2** (correctness). A match exits 1
first. Then 3 when no staged blob is text, so a binary-only commit or merge
passes. Then 4 when no private-class source loaded, after scanning with any
public terms. Binaries are still scanned, as before, so a term inside one is
still refused. With `--message`, a missing file is 4.

**"Every location it probed" includes the walk** (correctness). The refusal
lists each private candidate the resolver considered and `.deny-terms.private`
in every ancestor directory the walk visited, which needed the walk's
directory list factored out of `resolution.py`.

**`filemode` writes with `--cacheinfo`, not `--chmod`** (correctness). The
proposal assumed `update-index --chmod` leaves the staged blob alone. Measured
on git 2.43.7, it does not: given a path it re-reads the working file, so the
unstaged half of a partly staged file was committed. The test for that
criterion failed on both hosts until the write named the staged blob
explicitly. The removed tool's hook carries the same defect.

**The rule reads the staged blob and acts only on regular files**
(correctness). The removed hook read the first bytes of the working file and
would try to change the mode of any staged path, symlinks included. The
staged blob is what is committed, and 120000 or 160000 entries have no
executable bit to set.

**The `core.fileMode = false` refusal is not carried over** (correctness).
The removed hook refused such commits; the proposal's design reports on
`core.fileMode` rather than refusing on it, and `--cacheinfo` records the
intended mode whatever that setting says.

**A command missing from PATH refuses whether or not the check is required**
(diagnosability). A declared check whose program is gone is a broken install,
and passing quietly would be the "resolves to nothing" case the proposal
rules out for ids.

**Every enabled check runs even after one refuses** (diagnosability). One
commit attempt then reports everything wrong with it.

**Settings file names and locations** (default, following the operator's
layered-configuration standard). System `/etc/git-hygiene.conf`, then
`git-hygiene/config` under each `$XDG_CONFIG_DIRS` entry; user
`$XDG_CONFIG_HOME/git-hygiene/config`; declarations under
`$XDG_DATA_HOME/git-hygiene/checks/*.conf` and each `$XDG_DATA_DIRS` entry.
Both XDG lists split on `os.pathsep`, since a colon would cut a Windows drive
letter off its path.

**No whole-file override (`--config`, `GIT_HYGIENE_CONFIG`)** (correctness).
The operator's standard offers one, but it would let a single variable drop
the tracked layer, and this proposal makes the tracked layer the one place a
repository can require a check.

**Environment and flag syntax** (default). `GIT_HYGIENE_ENABLE`, `_DISABLE`,
`_REQUIRE` and `_OPTIONAL` take comma- or space-separated ids, with matching
repeatable flags. Naming one id both ways in the same layer is a usage error
rather than a silent tie-break (robustness).

**An `include` key in a settings file warns and is skipped** (diagnosability).
`--no-includes` already stops git following it; rejecting the file outright
would make a harmless line fatal, and ignoring it silently would hide it.

**`install-hooks` installs what the registry needs and removes the rest**
(correctness, per the operator's idempotency standard). A shim is written for
`pre-commit`, `commit-msg` and every hook a declaration names; marked shims for
other hooks are removed. A registry it cannot read is exit 2.

**`--version` reads package metadata on 3.8 and newer** (correctness). The
generated `_version.py` uses syntax the 3.6 floor cannot import, and mypy at
the floor cannot see it; below 3.8 the version prints as `unknown`.

**The sdist test builds from a copy of the working tree, committed and
tagged** (correctness). That is what a release build sees, and it works before
the change under test is committed. `setuptools` and `setuptools_scm` joined
the dev extra for it; the 3.6 replica has neither, so there the test skips with
that reason and the Windows run is the local proof.

**The spike was built as a separate work package** in its own worktree and
merged first, since nothing else depended on it.

## Addendum, 2026-09-16, measured at the floor

Two statements under "Alternatives considered" do not survive measurement on
the RHEL 8.10 replica. `pre-commit` can be installed at the floor: 4.6.2
cannot, but 2.17.0 declares `>=3.6.1`, installs on Python 3.6.9, and runs
this repository's hooks once the manifest admits it (decision 0015,
`spike/pre-commit-at-floor`). Its git requirement is no obstacle either,
since the `--deduplicate` call arrived only in 4.6.1.

The same spike records how the framework treats a check that changes only
an index mode. With `core.fileMode` true, the first commit is refused with
"files were modified by this hook" and the second lands with the corrected
mode; with it false, the first commit lands. The goal here, a corrected mode
on the first commit whatever the setting, is therefore not met by the
framework.

Whether those findings change the choice of a custom front end is left to
the operator; this addendum corrects the record and does not reopen it.
